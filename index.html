    Choose the simplest structure that holds, and draw the system before writing it.

  3. 03

    Development

    Small, reviewable changes, with one source of truth for anything shared.

    here One knowledge model drives the system map, the command palette and the assistant.

  4. 04

    Integration

    Connect external services behind clear contracts, and plan for them failing.

    here The contact form posts to Web3Forms; if that fails, a prefilled email link takes over.

  5. 05

    Testing

    Automate whatever a person would otherwise have to check by hand.

    here Playwright end-to-end tests on desktop and mobile, plus HTML, CSS and JavaScript linting.

  6. 06

    Deployment

    Every change passes review and an automated gate before it ships.

    here Pull requests run CI; Vercel deploys previews and production, and GitHub Pages mirrors it.

  7. 07

    Monitoring

    Check what people actually receive, after it ships, not only before.

    here Every deployment triggers a smoke test against the live URL.

  8. 08

    Optimisation

    Measure first, then improve what the numbers point at.

    here Lighthouse budgets in CI, with accessibility at 100 and zero main-thread blocking.

04/ Observatory

Visual intelligence observatory

First, what a real model returned. Then a rule lab where you set the threshold and the rules, and watch a frame travel from camera to alert.

inputmodel output
real · Detectify notebook

What the model actually returned

  1. motobike0.70
  2. car0.36
  3. yellow_light0.47the lights are red

Detectify's vehicle model, on a frame it never saw in training. It finds the motorbike with confidence, but reads the red signals as yellow. A red-light rule fed by this output would stay silent: a miss caused by classification, not by the threshold. That is the kind of failure the rule lab below lets you explore.

Input side: the helmet model's pass over the same frame, which found nothing, so nothing is drawn.

simulated Rule lab: camera → stream → model → detection → event → alert

simulated Sample frames with pre-computed detections. No camera or model runs here; the threshold and the rules do, in your browser.

  1. camera--:--:--.---
  2. stream--:--:--.---
  3. model--:--:--.---
  4. detection--:--:--.---
  5. event--:--:--.---
  6. alert--:--:--.---

  1. A frame arrives. In a deployment it would come from an IP camera; here it is a drawn sample.

  2. Frames travel as a stream. A relay such as MediaMTX lets a model and a dashboard read the same feed.

  3. A single-pass detector, such as YOLO, reads the whole frame at once, after pre-processing.

  4. Each object comes back as a box, a class and a confidence score. The threshold decides which ones count.

  5. Rules turn detections into an event: a car past the stop line on red, a rider without a helmet.

  6. Anything that breaks a rule becomes an alert for a person to review.

0.50

Detections below the threshold are dropped before any rule sees them.

Rules
Event log

    inference

    Running a trained model on a new frame to get boxes, classes and confidence scores. Training happens once, on labelled data; inference happens on every frame.

    edge processing

    Running that inference on a device next to the camera, such as a Raspberry Pi, so events travel over the network instead of video: lower latency and bandwidth, at the cost of smaller models.

    what is real here

    The comparison above is real model output from Detectify. The rule lab uses drawn frames and pre-computed detections; its threshold, rules, log and alerts run live in your browser.
